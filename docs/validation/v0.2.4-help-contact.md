# v0.2.4 — Aide & contact

## Périmètre et architecture

La page /b2b-app/contact distingue deux destinataires. Le lien reste accessible à toute session B2B authentifiée, dont READ_ONLY. Le support prépare un message dans le client mail local ; les demandes à l’administrateur sont persistées dans MongoDB, dans l’organisation validée par le BFF.

Le support utilise une constante frontend publique (supportAddress dans contact.ts), un destinataire fixe et uniquement le texte saisi. Objet limité à 100 caractères, description à 800, URL encodée à 2 000 caractères. Les caractères de contrôle sont refusés ; la description accepte LF/tabulation. Un dépassement d’encodage propose la copie, avec un champ sélectionnable si le presse-papiers est refusé. Aucun appel API support, envoi automatique, stockage serveur, collecte de logs ou informations d’identité n’est ajouté. L’ouverture du mailto indique que l’utilisateur doit vérifier puis envoyer son email.

Le contact interne suit : commandes de domaine → service d’autorisation → port → repository Mongo → routes BFF → contrats Vue. Il réutilise la transaction Mongo existante et ses barrières de révocation des utilisateurs, organisations et memberships. Aucun appel LLM, ORDER, stock, RAG, Keycloak ou fournisseur de messagerie.

## Contrat d’API

Toutes les routes utilisent /b2b/api/contact.

| Méthode et suffixe | Effet et contrôle |
| --- | --- |
| POST /requests | Création avec operation_id, subject, category, description ; tenant/auteur issus du contexte |
| GET /requests | scope=own par défaut ; organization réservé à ORGANIZATION_ADMIN ; filtre open/resolved |
| GET /requests/{id} | Auteur ou administrateur du même tenant ; sinon 404 |
| GET /requests/{id}/replies | Même contrôle, réponses paginées |
| POST /requests/{id}/replies | Réponse de l’administrateur de l’organisation uniquement |
| POST /requests/{id}/status | Transition open/resolved par l’administrateur uniquement |

Listes : items, total, has_more, limit (1–100), offset (0–10 000). Tri des demandes : created_at DESC, request_id DESC ; réponses : created_at ASC, reply_id ASC. Comptage et lecture partagent le snapshot Mongo autorisé.

Les corps refusent les propriétés supplémentaires, dont organization_id, created_by, permissions et attachment. Objet interne limité à 120 caractères ; description/réponse à 4 000 ; contenu non vide, catégories fermées, contrôles refusés. Le texte est rendu par interpolation Vue, sans HTML interprété. Les identifiants de demandes et réponses sont des UUID aléatoires opaques. Aucun destinataire n’est déduit depuis Keycloak.

Les mutations passent par la protection cookie BFF, Origin et CSRF existante. Un Origin explicite hostile est aussi refusé sur les nouvelles lectures. Toutes les permissions et le contexte sont revérifiés avant l’opération et avant la restitution.

## Permissions

| Rôle | Permissions Contact |
| --- | --- |
| READ_ONLY, USER, MANAGER | contact:create, contact:read_own |
| ORGANIZATION_ADMIN | Les précédentes, contact:read_organization, contact:reply_organization, contact:manage_organization |

MANAGER ne reçoit aucun traitement administratif. Le tableau d’administration ne couvre que le tenant courant. Une demande d’un autre auteur est invisible à un USER du même tenant.

## Spam, concurrence et résultat incertain

Le registre d’opérations est durable et possède une clé unique (organisation, utilisateur, operation_id). L’empreinte inclut action et contenu. Un rejeu identique renvoie le reçu ; un contenu différent renvoie 409. Rejouer une ancienne transition ne réapplique pas son état après une réouverture ultérieure.

Les quotas sont contrôlés dans la même transaction que la création, derrière les barrières d’identité/organisation : 5 créations par utilisateur sur 10 minutes, 50 par organisation sur une heure, 20 réponses et 60 transitions par administrateur sur une minute. Un reçu existant est vérifié avant le quota. Les dépassements renvoient 429 et Retry-After: 600 (attente volontairement conservatrice).

Le frontend désactive les doubles soumissions et fige la clé et le corps pendant un résultat incertain. Le nouvel essai explicite reprend exactement ces valeurs ; aucun retry automatique. Cette reprise est disponible tant que la page reste ouverte. Les corps privés et clés Contact ne sont pas persistés dans le navigateur. Après fermeture ou expiration, consulter les demandes enregistrées avant une nouvelle saisie ; une réconciliation après rechargement n’est pas fournie en V1. Changement de compte/tenant, expiration et démontage effacent données et brouillons en mémoire ; les réponses tardives sont écartées.

## Migration additive et ordre d’intégration

Cette PR indépendante ajoute 0006_b2b_contact.json, sans modifier 0001 à 0005 :

- b2b_contact_requests : clé unique tenant/request, index de liste auteur et organisation.
- b2b_contact_replies : clé unique tenant/reply, index des réponses par demande.
- b2b_contact_operations : clé unique tenant/user/operation, index des quotas.
- Validateurs stricts ; aucune suppression, aucun TTL, aucune pièce jointe.

Aucun DDL au démarrage : une migration explicite réussie est requise par le repository. Le CLI existant et les fixtures restent limités aux bases jetables décrites dans [les migrations MongoDB](../mongodb-migrations.md). Aucun contournement de cible de production n’est introduit.

Couverture ajoutée : matrice de rôles, entrées invalides/identité forgée, isolation organisation et auteur, Admin API BFF, CSRF/Origin, révocation, quotas durables et concurrents, doubles soumissions, rejeux incompatibles et après réouverture, pagination >100 demandes, réponses paginées, migration additive répétable et conservation ORDER/stock. Les tests navigateur sont des fixtures de contrat, sans SSO ni base ; ils ne prouvent pas un déploiement ni une qualité Ollama.

Résultats locaux après rebase sur main incluant #75–#77 et réconciliation de 0006 : 3 797 tests backend et 370 sous-tests réussis, 626 tests d’intégration désélectionnés ; 122 cas déterministes sans échec ; 618 tests frontend ; typecheck, lint et build réussis ; 54 scénarios Chromium réussis.
