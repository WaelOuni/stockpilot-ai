## Architecture et périmètre

/b2b-app/ fournit une racine Vue distincte : compte/login, catalogue, commandes,
stock/mouvements/imports. Le client historique JWT et ses routes restent inchangés.
Transport BFF same-origin /b2b/auth et /b2b/api exclusivement, cookies include,
CSRF, décodage des réponses unknown, abort/timeout bornés et génération de session. Les lectures Vue portent aussi le CSRF de la session
restaurée ; le BFF refuse une preuve différente si le cookie a changé dans un
autre onglet. BroadcastChannel propage le logout quand disponible.
Les retours callback/logout sont fixes vers Vue seulement en mode métier opt-in ;
le mode auth_test conserve ses anciens contrats. Le nom d’organisation est relu
dans le repository serveur ; l’UI affiche l’ID utilisateur faute de profil humain.

Aucune nouvelle route métier backend, migration, dépendance runtime ou ouverture
de production_saas. Les transactions, fences, ownership et plafonds B1/B2/B3 sont
réutilisés. [Contrat utilisateur et limites](../b2b-user-guide.md).

### Campagne navigateur réelle

verrouillées présents :

```sh
(cd frontend && npm ci && npm run build)
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/tests/validate_bff_keycloak.py --frontend
```

Keycloak26.8.1 réel, client confidentiel et PKCE, BFF réel, Mongo8 replica set tmpfs,
Vue **build de production** réellement servie sous HTTPS. Composition ASGI
strictement de test, pas installation/proxy de production. Certificat éphémère
vérifié par HTTPX/Node et épinglé via SPKI dans Chromium ; aucune désactivation
globale TLS. Keycloak loopback HTTP utilise localhost, BFF HTTPS utilise127.0.0.1 :
les cookies serveur ne sont pas transmis à l’hôte fournisseur.

même SKU, prix/stocks distincts. Aucun callback ne provisionne une identité.

inconnu, rotation, reprise BFF, révocation, suspension et indisponibilité fournisseur.
