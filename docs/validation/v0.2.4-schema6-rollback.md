## Cause et choix

MigrationRunner.validate() vérifie l'historique complet, même lorsqu'un adapter
demande seulement require_version(1), (2) ou (3). Le registre v0.2.3 comporte
quatre versions : un historique à six entrées est refusé. Ignorer les versions
futures ou tronquer l'historique affaiblirait ce contrôle.

Le candidat API est un NOUVEAU build depuis les blobs Git v0.2.3 immuables.
Il incorpore exactement trois adaptations :

| Fichier relatif au package Mongo | Adaptation | SHA256 résultant |
|---|---|---|
| schema_migrations.py | Les cinq noms ajoutés à B2B_COLLECTIONS ; aucune autre instruction changée | d8ab260918a7165dd88ef06e723bf6346601cbf9172118244f5ca3af79236417 |
| migrations/0005_b2b_order_archives.json | Copie exacte du main approuvé | cef28bc9a1b42157299475168ca9268f82afa7146703d07b41622db049a253ec |
| migrations/0006_b2b_contact.json | Copie exacte du main approuvé | b76e9c8a5ca86adcddea9ce4d106bc3d218e32bae015cbfd77b40e7a51146146 |

Le runner v0.2.3 original a pour empreinte
e7feba6924844e736dcf8fdf37808954b5dd63d26135dabe4e71a3a2af8862d6.
Une comparaison AST impose que seule l'allowlist change ; les checksums imposent
aussi les octets officiels. Les fonctionnalités Archive/Contact et la grammaire
ORDER v0.2.4 ne sont pas incorporées. Les routes nouvelles sont réellement
testées comme absentes (404) dans l'image candidate.

Les anciennes pages Web doivent accompagner cette API : ne pas servir une
interface v0.2.4 qui propose Contact/Archive avec l'API de rollback.
Les sources v0.2.3 de router/index.ts, B2BHeader.vue et OrdersView.vue ont été
relues : aucune route Contact ou action d'archivage/restauration de commande.
Le scénario serveur ne vaut pas recette navigateur de l'ancien Web déployé.
Keycloak reste 26.8.1 ; aucune récupération administrative ni modification de
realm réel n'appartient à cette PR.

## Construction reproductible, sans publication

Prérequis : checkout existant contenant les objets des deux commits et du tag
annoté vérifié, Docker Linux local sur socket Unix, espace disponible et aucune
image locale portant déjà le nom calculé. Ne pas activer une installation
protégée pour obtenir Docker. Le job containers utilise son runner jetable.

~~~sh
# Lecture / préparation seulement, sans moteur Docker :
python3 scripts/ops/schema6_rollback.py --output /tmp/schema6-source.json

# Nouvelle construction locale, uniquement avec l'autorisation correspondante :
python3 scripts/ops/schema6_rollback.py --build --output /tmp/schema6-build.json
~~~

Chaque destination de preuve doit être inexistante. Les scripts refusent
l'écrasement. La première commande ne construit pas d'image et n'est pas une
qualification d'exécution. La seconde construit baseline et candidat, épinglés
linux/amd64, depuis le Dockerfile et requirements.lock v0.2.3 inchangés.
La base Python est déjà épinglée par digest dans ce Dockerfile.

Le contexte est construit hors dépôt depuis une allowlist de blobs :
Dockerfile, .dockerignore, requirements.lock, src/stockpilot.
Ni .git, .env, sauvegarde, fichier de travail, lien symbolique ou sous-module.
Il est supprimé en sortie. La comparaison SHA256 de TOUS les fichiers applicatifs
dans l'image construite refuse omission, ajout ou modification inattendue.

Labels OCI source et revision (commit v0.2.3), plus io.stockpilot.rollback :
migrations, context et qualification. Les noms locaux sont
stockpilot-rollback-baseline:<empreinte-contexte> et
stockpilot-rollback-candidate:<empreinte-contexte>. Aucun latest, SemVer officiel,
login GHCR, push ou publication. L'ID sha256 local est une empreinte de
configuration d'image, PAS un digest de manifeste GHCR ni l'ancien digest v0.2.3.

Empreintes des contextes mesurées localement :
- Baseline : cd3eb608fa1616803d54f578d03d40d8ef3c38c9200a4e58c1ffbf501699cba0 (212 fichiers).
- Candidat : 9e79e409ec9e85ef2552f242cb6e7639409ac06046a9a064bbd6e9f80821cb6c (214 fichiers).

La reproductibilité concerne sources, dépendances verrouillées, plateforme,
base et transformation. Aucune promesse de digest Docker bit-identique entre
builds : les métadonnées/horodatages et labels de qualification peuvent varier.
Conserver les empreintes de l'image effectivement testée avant toute future
promotion, qui demande une autorisation et une publication protégée distinctes.

## Campagne réelle par images

~~~sh
# Les images current et Keycloak sont celles construites depuis le checkout contrôlé.
python3 scripts/ci/qualify_schema6_rollback.py \
  --build-report /tmp/schema6-build.json \
  --current-image stockpilot-api:ci \
  --keycloak-image stockpilot-keycloak:ci \
  --output /tmp/schema6-qualification.json
~~~

La CI l'exécute obligatoirement dans containers, sans publier. Les autres quatre
jobs requis sont conservés. E2E historique reste skipped. Les deux JSON assainis
sont conservés quatorze jours dans l'artefact schema6-rollback-proof, même après
échec : toujours lire success et les phases, jamais la seule présence de l'artefact.

Le harnais crée ses ressources UUID avec labels de propriété :
deux réseaux internes, zéro port publié, Mongo replica set et deux PostgreSQL
en tmpfs par côté, plus Keycloak et les processus API de test.
Aucun volume persistant/anonymous n'est admis. Images, montages, réseaux et IDs
effectifs sont relus avant commande et nettoyage. Le socket Docker n'est pas
monté dans les images. Un serveur distant ou ressource préexistante est refusé.
Les cibles passent aussi par tests/integration_targets.py et les gardes des
runners applicatifs, sans les assouplir.

1. Baseline v0.2.3 réelle : schéma v4 explicitement appliqué sur la base vide,
   organisations A/B, utilisateurs/rôles/memberships/acheteurs, produits actifs
   et inactifs, commandes préparées/réservées/annulées, reçus et mouvement.
   PG : migrations, documents RAG, conversations et checkpoints synthétiques.
2. Version actuelle : application explicite de 0005 PUIS 0006. Comparaison
   intégrale des collections préexistantes, options, index, données et historique.
   Réapplication idempotente vérifiée sans modification.
3. Création Archive/Contact via HTTP BFF : archive conservée, autre archive
   restaurée, demande, réponse admin, statut et reçus. Refus des autres tenants
   et des permissions insuffisantes.
4. Ancien binaire inchangé : refus de v6 sans effet.
5. Candidat compatible : lifespan réel, sessions conservées, connexion
   Keycloak HTTPS réelle, Authorization Code/PKCE/nonce/JWKS, refus du callback
   rejoué. TestClient transporte les requêtes BFF en processus ; aucun proxy
   Nginx ou navigateur Windows n'est simulé comme réellement qualifié.
6. Catalogue/SKU/stocks/commandes/opérations, permissions, CSRF, Origin,
   isolation A/B, RAG et checkpoints via les adapters réels. Un tour assistant
   v0.2.4 avec catalogue_search est créé par le graphe réel (routage stock
   déterministe sans modèle), lu/rejoué par v0.2.3 et retrouvé complet au retour.
   Préparation sans réservation ; confirmation explicite concurrente à clé
   constante ; annulation/rejeu sans double réservation.
7. Versions v7, trou d'historique, checksum, état started, index inattendu et
   validateur incompatible refusés sur des COPIES jetables distinctes.
   Mauvaise confirmation et nom protégé refusés sans créer ce nom.
   Aucun correctif automatique d'historique.
8. Retour au code courant sur la même base v6 : archives, réponses/statut,
   idempotence, données, comptes et rôles restent utilisables. Pas de downgrade.

La surveillance des commandes Mongo refuse tout DDL pendant le lifespan BFF
et les requêtes. Les seules variations attendues sont les nouvelles transactions
synthétiques demandées, les fences d'autorisation, les sessions/transactions
OIDC et deux incréments de révision du produit lors de réservation/libération.
Les données Archive/Contact, les anciennes commandes/reçus, PG et les
identités hors fences sont rapprochées. Les comparaisons ne confondent pas
une égalité de compteurs avec une égalité de documents.

## Sauvegarde/restauration synthétique et limites privées

Après arrêt des écrivains jetables, mongodump dynamique inclut TOUTES les
collections, y compris les cinq nouvelles et le registre/lock.
Deux pg_dump format custom capturent application et Keycloak réel ; les globals
sans mots de passe sont également capturés. Les rôles synthétiques identiques
sont préprovisionnés sur la restauration ; leurs attributs sont rapprochés.
Ce test ne qualifie pas le provisioning d'ACL/rôles arbitraires d'une installation.

Empreintes SHA256 et tailles des archives ; BSON Extended JSON canonique typé
(Int32/Int64/double distingués), inventaire logique avant/après dump ;
restauration sans drop sur trois instances vides indépendantes ; comparaison
de tous les documents/lignes, options/validateurs, ordre des clés d'index Mongo,
colonnes/index/contraintes et séquences PostgreSQL, historiques de migrations.
Keycloak restauré démarre sans import de realm ; connexion OIDC et lecture des
données restaurées sont répétées. Aucun nombre fixe 14/10/101 n'est imposé.

Les archives et secrets sont synthétiques, privés dans le répertoire temporaire,
jamais joints à la PR ou aux artefacts CI. Les preuves ne contiennent que checks,
empreintes et structures. Le nettoyage conserve la preuve assainie et supprime
uniquement les ressources créées, sans prune. Les images de qualification
restent locales au runner jetable ; aucune image distante n'est créée/supprimée.

Sources examinées : scripts/tests/canonical_backup.py inventorie déjà Mongo
dynamiquement ; ses comparaisons PG historiques ne prouvent pas seules les
index/contraintes (la présente campagne les ajoute dans son propre harnais).
Les opérateurs privés backup_fresh.py / restore_isolated.py ne sont pas dans le
dépôt. Leur compatibilité n'est donc PAS qualifiée.

Contrat à vérifier lors d'une future mission opérateur autorisée :
- identité installation, composition effective, images, volumes, espace et écrivains ;
- inventaire dynamique, cinq collections nouvelles + registre + options/index ;
- Mongo, PG applicatif et PG Keycloak appariés sous quiescence vérifiée ;
- rôles/ACL/extensions/séquences/configurations privées nécessaires, sans exposition ;
- SHA256 et transport vérifié, copie externe chiffrée distinctement autorisée ;
- restauration indépendante vide, aucun port exposé, puis comparaison logique et
  structurelle complète, OIDC et parcours métier ;
- disponibilité de l'image candidate EXACTEMENT qualifiée, de l'ancien Web et
  de Keycloak, avec Compose/configuration réellement capturés sur la VM.
Le backup v0.2.3 historique ne contient pas les futurs documents Contact/Archive.
Une restauration de backup ancien effacerait des écritures et n'est pas un
rollback applicatif acceptable.

## Spécification du futur opérateur de migration réelle (non implémenté)

La CLI actuelle migrate.py exige URI explicite, nom jetable UUID, endpoint
loopback distinct du port applicatif et répétition exacte de la confirmation.
Le runner exige aussi serveur sans bases/marqueurs protégés, primary, historique
intègre, lock exclusif propriétaire avec échéance, aucun takeover.
Ces limites sont INCHANGÉES. Ne pas exécuter la commande de test sur la VM,
renommer une base ou altérer le regex pour la faire accepter.

Un futur opérateur approuvé séparément devra :
1. vérifier SSH/identité d'installation et identité de la base, configuration
   effective, empreintes code/migrations, rôle DDL distinct et autorisation exacte ;
2. exiger sauvegarde fraîche appariée + restauration isolée qualifiée et preuves ;
3. fermer les mutations puis drainer tous les écrivains, vérifier les opérations
   en attente et leur issue, conserver les clés idempotentes ;
4. prendre un lock exclusif sans takeover d'un lock expiré ; revalider l'historique
   v4 et toutes les structures, refuser toute dérive ;
5. appliquer uniquement les définitions approuvées 0005 puis 0006, vérifier chaque
   structure avant de marquer succeeded, préserver les historiques précédents ;
6. arrêter sur résultat incertain, lock perdu, erreur réseau ou DDL partielle.
   Pas de relance/réparation automatique, ni suppression de lock/historique ;
7. revalider v6, données préexistantes et disponibilité du rollback testé avant
   reprise ; gates six services, HTTPS/issuer/OIDC/sessions et recette B2B ;
8. conserver un rapport assaini lié aux images et au code réellement exécutés.

Un failed/started ou schéma partiel est un incident de migration, pas un problème
que ce candidat répare. Conserver la quiescence et ouvrir une reprise humaine
distincte. La présente PR ne fournit aucune voie d'application sur base réelle.

## Procédure future de rollback applicatif (non exécutée)

Préconditions : migration v6 entièrement succeeded, candidat qualifié et publié
par mécanisme approuvé, digests Web/Keycloak vérifiés, configurations préservées,
sauvegarde actuelle restaurable, fenêtre et autorisation explicites.

Sous quiescence bornée : confirmer absence de pending non réconcilié, conserver
les bases v6 et toutes leurs écritures, remplacer uniquement l'API par le digest
du candidat et le Web par son digest v0.2.3 approuvé. Aucune migration inverse,
SQL/Mongo direct, suppression, import realm ou restauration automatique.
Les nouvelles fonctionnalités sont indisponibles mais leurs données restent.
Les sessions sont conservées si les mêmes clés/configurations/issuer et bornes
d'expiration restent valides ; aucune prolongation implicite n'est promise.

Vérifier catalogue/SKU/stocks, historiques/permissions, OIDC et BFF, compteurs
et empreintes appropriés. Revenir à v0.2.4 avec ses images approuvées, revalider
v6, retrouver Archive/Contact et les mêmes reçus. Si un gate échoue : arrêt,
diagnostic et intervention distincte ; jamais affaiblir le validateur.
