~~~sh
sudo .venv/bin/python -B scripts/tests/qualify_private_recovery.py \
  --source-directory "<copies-privees-des-trois-sources-epinglees>" \
  --api-image "<image-API-locale-verifiee>" \
  --web-image "<ancien-Web-local-verifie>" \
~~~

## Opérateur de transition propre à cette installation

Deux modules installés seulement après revue/CI :
- scripts/ops/v024_installation_migration.py : machine d'états Mongo 0005/0006.
- scripts/ops/execute_v024_migration.py : admission hôte et exécution dans le candidat.

Le CLI jetable et MigrationRunner.apply restent inchangés. L'opérateur utilise les
définitions immuables et leurs validateurs publics, sans appeler leurs méthodes
privées ni contourner la garde de cible du CLI.

Le plan privé root:root 0600 sous /opt/stockpilot/evidence doit contenir exactement
les champs PLAN_FIELDS du module, notamment :
- format stockpilot-v024-migration-plan-v1 ;
- installation, empreinte SSH vérifiée, autorisation MIGRATE STOCKPILOT-B2B-v021 0005 0006 ;
- SHA final approuvé ; dates avec timezone, fenêtre maximale de deux heures ;
- attestation d'absence d'écrivain externe datant de moins de dix minutes ;
- SHA256 du Compose actif, operator.json et des trois modules exécutés ;
- chemin exact du nouveau backup, SHA256 indépendant de son manifeste v2 ;
- preuve de restauration de ce backup, son SHA256 et ses trois IDs distincts ;
- ID immuable du candidat chargé, empreinte du contexte, identité Docker.

Ne pas inventer ces valeurs : les extraire des preuves de la fenêtre et du dépôt
approuvé. Les mots de passe proviennent exclusivement du montage privé operator.json.

~~~sh
# VM, seulement après admission complète, backup/restauration de cette fenêtre,
# arrêt explicite de bff/keycloak et revue du plan réel.
sudo python3 -B /opt/stockpilot/operations/execute_v024_migration.py \
  "<plan-prive-root-0600-sous-opt-stockpilot-evidence.json>"
~~~

L'opérateur ne suspend, ne reprend et ne déploie aucun service. Il exige :
- lock hôte partagé avec backup/restore ;
- provenance active identique à la capture v2, schéma v4, restauration prouvée ;
- six IDs et volumes sources identiques, BFF/Keycloak arrêtés ;
- bases/proxy healthy, bases sans ports publiés, aucun autre client réseau ;
- runtime candidat exact, plateforme, provenance et code vérifiés ;
- égalité stricte de la capture avant transition avec le backup, y compris Keycloak ;
- absence de connexion cliente PostgreSQL supplémentaire et de transaction préparée ;
- cible Mongo fixe, primary/replica set/identité, six checksums approuvés ;
- aucun lock Mongo, même expiré, aucun historique incomplet/pending.

Seules 0005 et 0006 peuvent être créées. Une collection déjà présente est refusée.
Chaque définition est relue avant succeeded ; données historiques et PostgreSQL
restent identiques. Une migration partielle garde le verrou pour récupération
contrôlée. Aucun takeover, drop, collMod, réparation, migration inverse ou relance
automatique. Le conteneur sorti est conservé comme preuve privée ; le nettoyage
éventuel doit vérifier son ID, son label et ses montages.

Si Keycloak ou des écritures métier ont changé depuis le backup, le rapprochement
strict échoue : ne pas ignorer les tables ni fabriquer une égalité. Maintenir le
point d'arrêt sûr et établir une nouvelle capture cohérente qualifiée ou un
changement opérateur séparément testé. Aucun backup ancien restauré automatiquement.

Tests spécifiques : transition sur vrai Mongo jetable (succès/rejeu sans écriture,
échecs 0005/0006, perte de lock, concurrence, checksum, identité et historique) ;
admission hôte par simulations locales négatives ; point d'entrée réel en conteneur
sur trois bases restaurées synthétiques. Ces preuves ne valent pas migration VM.

## Gates de release et de bascule

1. PR technique revue selon les protections main ; cinq checks du SHA final verts.
2. Candidat privé réellement disponible sur la VM, anciens Web/Keycloak conservés.
3. Tag annoté absent avant création ; dry-run officiel puis publication contrôlée
   des trois composants ; six tags/digests/labels/private vérifiés, draft seulement,
   flag RELEASE_PUBLICATION_ENABLED remis à false.
4. Préflight VM, backup frais restauré, opérateurs qualifiés installés avec originaux
   conservés, écrivains maîtrisés, plan exact admis.
5. Migration complète puis remplacement uniquement BFF/proxy par digests vérifiés.
   Keycloak actif conservé si fonctionnellement identique.
6. Six services, HTTPS, issuer, connexion réelle/PKCE/callback/session, isolation,
   lecture B2B et absence de mutation métier accidentelle.
7. Rollback éventuel unique avec candidat v6 et ancien Web, bases courantes conservées.
8. Sauvegarde finale v6 réellement restaurée, nettoyage ciblé, contrôles HTTPS/OIDC.

Une erreur partielle interdit la suite automatique. Le diagnostic Nginx 502 reste
borné ; aucune cause racine inventée ni reload implicite. La limite Schannel
CRYPT_E_NO_REVOCATION_CHECK reste distincte ; aucune désactivation TLS/révocation.

À cette étape documentaire, aucun tag/release v0.2.4, installation d'opérateur,
migration ou déploiement VM n'est attesté. Les résultats réels de l'intervention
doivent être consignés séparément, avec durées, SHA256 et état final.
