# v0.2.4 — Historiques complets et archives personnelles

Base indépendante : main aedb58fe91be092a6de1923e4c00e53c5ca089f2.
Cette PR n'autorise ni migration sur données réelles ni déploiement.

## Cause et interfaces

Les listes historiques exposaient seulement items/limit/offset et le bouton suivant
déduisait l'existence d'une page de la longueur reçue. Elles exposent désormais aussi
total et has_more, calculés dans le même snapshot Mongo après restriction tenant,
propriétaire et autorisation. Commandes : tri created_at DESC, order_id DESC ;
mouvements : occurred_at DESC, movement_id DESC ; imports : created_at DESC,
import_id DESC. Les trois vues réutilisent CataloguePagination, paramétré par libellés.
Première/précédente/pages/suivante/dernière, plage affichée, aria-current, FR/EN.

GET /b2b/api/orders accepte status=prepared|reserved|cancelled (omission : tous)
et archived=false|true (défaut false, préférence de l'utilisateur courant).
Les acheteurs autorisés sont filtrés avant le total. Les listes de mouvements et
imports gardent leurs permissions stock:read et import:execute.
Chaque page est courante ; l'ensemble de la navigation n'est pas un snapshot figé.
Limite 100, offset 10000 ; au-delà, le composant signale la limite.

POST /b2b/api/orders/{order_id}/archive et /restore exigent operation_id et
confirmed=true strict. Session, Origin, CSRF, tenant, droit de lecture et acheteur
sont revérifiés ; seul l'état cancelled est accepté. Aucune mutation de commande,
réservation, stock, preuve de préparation ou journal ORDER n'est faite.

## Persistance et idempotence

Migration additive 0005_b2b_order_archives :
- b2b_order_archives : unique (organization_id, user_id, order_id), archived bool,
  updated_at. La restauration conserve l'enregistrement avec archived=false.
- b2b_order_archive_operations : unique (organization_id, user_id, operation_id),
  empreinte de commande et résultat durable. Un ancien replay ne réapplique pas
  une préférence si une restauration plus récente a eu lieu.

Les identités sont issues du contexte serveur. Un manager autorisé peut archiver
une commande visible dans sa propre liste, sans la masquer aux autres utilisateurs.
Un résultat réseau incertain reste dans le dialogue ; le prochain essai explicite
réutilise la même clé. Aucun retry automatique, aucune suppression physique/TTL.
Les fences d'autorisation habituelles restent actives dans les transactions.

## Migration, sauvegarde et rollback

Les migrations 0001–0004 restent inchangées. Aucune DDL au démarrage.
Utiliser le CLI de migration existant pour plan/validate/apply sur des bases jetables
explicitement identifiées lors de la qualification :
```sh
# URI fournie par un mécanisme local protégé, jamais passée en argument.
python -m stockpilot.infrastructure.persistence.mongodb.migrate plan --database "$TEST_DB"
python -m stockpilot.infrastructure.persistence.mongodb.migrate apply --database "$TEST_DB" --confirm-disposable-database "$TEST_DB"
python -m stockpilot.infrastructure.persistence.mongodb.migrate validate --database "$TEST_DB"
```
Ses gardes refusent les bases
application/DEMO : cette PR ne les contourne pas et ne fournit pas une autorisation
d'application sur la VM.

Avant une future migration réelle : obtenir une autorisation distincte, définir
l'opérateur approuvé pour la configuration effective, réaliser une sauvegarde
appariée et une restauration isolée incluant les deux nouvelles collections,
leurs index et l'historique des migrations. Prouver les compteurs et empreintes
des commandes, réservations et mouvements avant/après.

Le rollback non destructif conserve ces collections et tous les reçus.
Attention : le code v0.2.3 refuse un historique de migrations inconnu.
Un retour fonctionnel nécessite donc un build revu conservant le registre 0005
tout en retirant/désactivant les nouveaux parcours, puis des tests sur restauration
isolée. Ne jamais effacer l'historique de migration ou restaurer automatiquement
les bases pour faire accepter une ancienne image. Le rollback vers le digest
v0.2.3 inchangé n'est pas qualifié après application de 0005.

La PR contact indépendante ajoutera également une migration depuis main.
L'ordre de fusion recommandé est historiques puis contact ; avant fusion de la
seconde, réconcilier sa numérotation et refaire la CI, sans changer une migration
déjà appliquée. Ne pas déployer deux migrations portant le même numéro.

## Validation et recette

Tests : confirmations strictes, filtre injecté, propriétaire/tenant/acheteur,
révocation, prepared/reserved refusés, replay et clé divergente, restauration,
ancien replay après restauration, absence d'altération des cinq collections métier.
Tests de pagination >100 commandes, filtres avant total, tris stables, listes
mouvements/imports indépendantes, HTTP Origin/CSRF. Les bases de test sont jetables.
Frontend : dernière page, reset filtres, page devenue vide, confirmation/retry ;
Playwright mobile FR/EN et régressions de comparaison/imports existantes.

Recette future autorisée : vérifier les listes sur deux comptes, archiver une
commande synthétique annulée avec confirmation, vérifier sa visibilité pour
l'autre compte, restaurer et comparer les empreintes métier. Aucun test ne doit
annuler une vraie commande pour créer ses données de recette.
Résultats exacts et CI finale consignés dans la PR.

## Retours CI sur les données synthétiques

La première campagne isolée a détecté deux défauts de fixtures : les dates utilisées pour recalculer une preuve de préparation étaient décodées sans UTC, et le test historique 0003→0004 incluait aussi la nouvelle migration. La fixture utilise maintenant le codec UTC du repository. Le scénario historique est borné aux quatre migrations d’origine, avec toutes ses assertions conservées ; un nouveau scénario 0004→0005 contrôle séparément données, validateurs, index, historique et répétition sans modification.

Le scénario de révocation d’association acheteur utilise le statut historique validé disabled (les memberships utilisent suspended). Le validateur Mongo a refusé cette confusion dans la fixture ; le contrôle de visibilité après révocation est conservé.
