### Rollback applicatif et restauration de données : décisions séparées

**Rollback applicatif** (fenêtre/GO prévus dans le changement) : suspendre les
écritures si nécessaire pour préserver les opérations en cours ; conserver les
données actuelles. Tant que l’image Keycloak personnalisée fonctionne, remettre
les paramètres UI précédents par l’administration Keycloak, puis vérifier le
GET/rendu. Cela évite de demander un thème absent à l’ancienne image officielle.
Ensuite seulement remettre la composition privée précédente revue :

```sh
curl --fail --silent --show-error --cacert "$CA_PEM" --header @"$KC_AUTH_HEADER"   -H 'Content-Type: application/json' -X PUT --data-binary @"$REALM_UI_ROLLBACK" "$REALM_URL"
sudo docker compose -f "$COMPOSE_ROLLBACK_APPROUVE" -p "$PROJECT" up -d --no-deps bff proxy keycloak
sudo docker compose -f "$COMPOSE_ROLLBACK_APPROUVE" -p "$PROJECT" ps --format json
```

Revalider six services, digests, volumes, HTTPS, OIDC, appartenance, commandes et
réservations actuelles. Aucun `down -v`, seed, downgrade inventé ou restauration DB.
Si Keycloak est indisponible et empêche la remise du thème, arrêter la procédure
nominale et faire qualifier une reprise administrative ; ne pas écrire directement
ses tables ni réimporter un realm pour accélérer le rollback.

**Restauration des bases** : réservée à un incident de données et à une décision
séparée. Elle exige sauvegarde cohérente, quiescence, nouvelle sauvegarde de l’état
incident, restauration isolée prouvée, RPO accepté et réconciliation des écritures
postérieures (commandes, réservations, imports, conversations). Restaurer un ancien
backup sur un simple incident applicatif perdrait ces écritures : c’est interdit.
Ne pas prétendre « sans perte » si ces conditions ne sont pas démontrées.
