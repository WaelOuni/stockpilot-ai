# V13.9.4-R1 — restauration physique avec propriétaires numériques

Base main vérifiée : `724655a6a0eae32d48c32a87ae485091f892e3c0` (#59).
Ce lot ne démarre aucun moteur de base et ne modifie ni la source, ni les anciens
clones, ni le bundle V13.9.3. Les preuves de campagne restent privées hors Git.

## Cause démontrée

Le moteur examiné est Docker Desktop 28.4.0. Le client transmet copyUIDGID pour
`docker cp -a`. Dans Moby, `tarCopyOptions` traduit le Config.User non vide du
conteneur en ChownOpts ; l'extracteur applique cette identité à tous les membres
au lieu de leurs UID/GID numériques. Les Uname/Gname TAR n'interviennent pas ici.
[Options](https://github.com/moby/moby/blob/v28.4.0/daemon/archive_tarcopyoptions_unix.go),
[appel](https://github.com/moby/moby/blob/v28.4.0/daemon/archive_unix.go),
[extraction](https://github.com/moby/moby/blob/v28.4.0/vendor/github.com/moby/go-archive/archive.go).

Le TAR Mongo contient réellement 100 fichiers UID/GID 0:0. Leur import dans un
conteneur Config.User=999:999 avec -a produit 999:999. Ce n'est pas une différence
de noms affichés : les nombres des headers relus divergent. À l'inverse, la
racine attendue 999:999 reste 0:0. Le code ignore explicitement le membre `.`
existant avant chown/chmod/mtime ; les racines PostgreSQL restent donc 0:0/0755
au lieu de 999:999/0700 et 70:70/0700. Un code retour 0 ne valide pas ces effets.

Le contrôle mountpoint était placé après toutes les copies dans l'adaptateur
V13.9.4. Il pouvait seulement détecter rétrospectivement une erreur de driver,
options ou alias physique ; les labels/noms UUID ne remplaçaient pas cette garde.

## Reproduction réelle sans archive privée

Deux TAR synthétiques : noms utilisateur/groupe vides puis contradictoires
(`root` avec UID/GID numériques différents). Neuf membres chacun : propriétaires
0, 70, 999 et 12345:23456 ; racine 0700, niveaux 0750/0755, répertoire 0500 et
fichiers 0400/0600/0640/0644, mtime fixe. Conteneurs sans réseau, aucun moteur DB.

| Méthode | Descendants | Racine | Résultat |
|---|---|---|---|
| TAR stdin docker cp -a, Config.User 999:999 | Tous forcés 999:999 | Inchangée 0:0/0755 | Défaut reproduit |
| TAR stdin docker cp sans -a, même utilisateur | UID/GID numériques conservés | Inchangée 0:0/0755 | Insuffisant |
| GNU tar 1.35 --numeric-owner --same-owner --same-permissions --delay-directory-restore | Tous identiques | UID/GID, mode, mtime identiques | 2/2 fixtures conformes |

Un premier helper de qualification a été refusé avant démarrage car Docker
renvoie CAP_CHOWN et non CHOWN. La comparaison normalise uniquement ce préfixe
standard ; toute capacité absente ou supplémentaire reste refusée. Le helper
refusé reste conservé. Aucun résultat inconnu transformé en succès.

## Correction limitée aux outils et au runbook

`scripts/b2b_physical_restore.py` valide digest, archive entière, chemins/types,
parents explicites et racine. Il refuse liens, périphériques, FIFO, doublons,
traversées, limites dépassées et métadonnées étendues non qualifiées. Les nombres
UID/GID/modes sont pris dans l'archive ancrée, pas déduits de noms d'utilisateur.

Le helper utilise une image applicative déjà présente par digest, sans VOLUME
implicite, avec `/bin/tar` comme unique entrypoint et des arguments figés. Aucun
code applicatif n'est exécuté. Rootfs RO, réseau none, zéro port/bind/socket,
restart=no, healthcheck désactivé ; seules capacités CHOWN, DAC_OVERRIDE, FOWNER,
FSETID. L'archive passe via stdin ; le bundle n'est pas monté.

Chaque volume est neuf et attesté immédiatement : nom/labels de campagne, driver
local, options vides, mountpoint unique disjoint de tous les préexistants. Le
helper créé est inspecté et le volume relu vide avant import. Un consommateur
inattendu refuse la suite. Le ledger est conservé hors bundle avant chaque
écriture et aucune ressource n'est supprimée automatiquement.

GNU tar restaure chaque propriétaire numérique et chaque mode, puis les dates
des répertoires, racine comprise. Aucun chown -R/chmod -R homogène ni correction
sur anciens clones. Une relecture Docker indépendante compare exactement tous
les chemins, types, contenus SHA-256, tailles, UID/GID, modes et mtime.

La section 3 du runbook existant appelle cet outil avec préflight/OCI préalable,
verrou, nouvelle preuve privée et ancre SHA256SUMS indépendante. Les moteurs
restent interdits. PHYSICAL RESTORE VERIFIED n'est pas une récupération validée ;
le bundle garde cold-physical-unvalidated.

## Validation et limites

Tests négatifs : chemins/parents/doublons, liens/hardlinks/spéciaux, xattrs,
UID/GID/modes invalides, TAR tronqué, limites, hash faux, volume existant/alias,
driver/options/labels, helper réseau/bind/moteur/capacités/consommateur inattendus,
conteneur étranger, destination non vide, code non nul/stderr/timeout ; refus
avant import vérifié. La relecture finale reste obligatoire même après tar code 0.

La restauration des données privées est conditionnée à une revue indépendante
positive, aux tests synthétiques et à un nouveau préflight. Son résultat et les
identités ne doivent être annoncés que d'après le manifeste privé exécuté.
ACL/xattrs non qualifiés sont refusés ; aucune cohérence logique, FCV, migrations,
WAL, journal, login ou transaction métier n'est validée par ce lot physique.

Validation locale ciblée finale : 18 tests et 22 sous-tests réussis. Deux revues
indépendantes ont aussi exercé huit refus supplémentaires, intégrés ensuite
aux tests permanents. La version finale avec TAR_OPTIONS vide et journal
des preuves avant import a été requalifiée sur deux nouveaux volumes
synthétiques : fidélité complète des deux fixtures, racines incluses.
Frontend : 510 tests, typecheck, lint, build réussis ; évaluations déterministes
122 cas sans échec. Aucun service de base local pour ces tests.

Suite Python complète : 3348 tests réussis, 511 intégrations désélectionnées,
un avertissement de clé HMAC synthétique ; contrôles ciblés finaux répétés
après whitelist PAX stricte. Aucune intégration DB locale lancée.
