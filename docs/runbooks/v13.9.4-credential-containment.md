# BFF configuration diagnostics and PostgreSQL credential containment

This procedure prepares a rotation. It does not authorize changing a database,
private file, manifest, authentication rule, running service or saved trace.
Stop when target identity, authentication behavior or secret scope is unknown.

## Safe configuration display

Use the bounded diagnostic instead of printing settings, environments, connection
strings or dictionaries selected by key substrings:

```sh
python scripts/b2b_safe_diagnostic.py --file "$PRIVATE_BFF_CONFIG_JSON"
```

`--stdin` also accepts a private JSON stream without echoing it. Do not put the
JSON, a password or an authenticated URI in a shell argument or environment.
Do not run with shell tracing or echo the stream before piping it.

Only a closed mode enumeration, exact booleans and bounded numeric settings are
displayed. URI/URL/DSN, origins, issuers, paths, IDs, databases, schemas, model
names and unknown keys are omitted, even when their values appear harmless.
An invalid allowed value is reported by status without echoing it. Input and
OS/JSON errors have a fixed response without the exception, path or input text.

An absent setting remains unknown. Exit zero means the projection completed;
it does not validate a connection, credentials, configuration or safe startup.
Invalid allowed fields or inconsistent supplied session bounds return exit2.
This tool is not a general secret detector, and does not inspect defaults or
import the application settings. It cannot make other raw-output commands safe.

The file input is a regular file, at most32KiB, with symlink components refused.
On POSIX it must belong to the current user and deny access to others; group
readability supports the existing private0640 runtime files. Windows ACLs are
not validated by this tool. It performs no write, network call or DB connection.

## Scope the exposed role without disclosing its credential

1. Identify the PostgreSQL role, database/cluster identity and consumers from
   public provisioning code. An equal role name in MongoDB is a separate account.
2. Compare candidate private values only in process memory. Emit booleans and
   role/category counts, never the URI, password, verifier, password length,
   substring, digest or matched source lines. Never search GitHub with a secret.
3. Include private BFF/operator configuration, their manifest fingerprints,
   archived private state, physical database copies and any other consumers.
   Distinguish verified equality from inferred physical-copy lineage.
4. Inspect existing access boundaries and available authentication evidence in
   read-only mode. No observed failure or active session does not establish that
   no unauthorized historical access occurred. Logging may be disabled.
5. Preserve original evidence in place. Record only redacted locators, time and
   scope, restrict dissemination, and do not export full Codex transcripts/logs
   into issue trackers, feedback, CI or Git. Trace deletion, ACL changes and
   remote-retention requests need a separate decision. Archiving is not erasure.

## Targeted rotation plan: requires separate authorization

For the canonical local installation, the PostgreSQL application role is
`stockpilot_bff`. Its consumers are private `bff.json` at
`BFF_ASSISTANT_POSTGRES_URI` and private `operator.json` at `app_pg_password`.
The private manifest anchors both files. Do not rotate administrator `ci`, the
Keycloak DB account, the MongoDB namesake, OIDC client credentials or the BFF
configuration/session key merely because they are in the same installation.
Expand scope only on evidence of actual reuse.

1. **Approve the exact target and window.** Record container/volume identities,
   cluster identity, role OID/attributes/grants and consumer files. Originals
   that are stopped stay stopped until a new authorization explicitly permits
   the required source operations. Do not temporarily start them to inspect or
   rotate during containment. Each physical clone is an independent auth domain.
2. **Qualify authentication first.** Inspect the first matching HBA rule for the
   intended test endpoint and prove that it requires SCRAM. Local peer/trust and
   loopback trust do not validate passwords. A disabled TCP listener or network
   failure is not a negative credential test. Necessary listener/HBA/network
   changes require explicit approval; never weaken authentication to pass.
3. **Quiesce only approved consumers.** Keep the BFF stopped or drain its pool
   and prove no remaining application sessions. Password rotation does not
   revoke authenticated sessions. Targeted session termination, if required,
   needs authorization and must not affect administrator or Keycloak sessions.
4. **Stage private state without activation.** Under the installation's existing
   cooperative lock, generate a high-entropy value with a CSPRNG in memory or an
   approved secret store. Never display it, put it in argv/environment/history,
   or write it to Git/test fixtures. Use per-domain secrets rather than reusing
   one value across clones. Stage only the two consumer fields and the resulting
   manifest fingerprints in a new private directory, exclusive no-follow files,
   preserving the required owner/group/modes. Leave originals intact at this step.
5. **Change only the password in the approved database.** Use a verified
   administrative connection and compute a salted SCRAM verifier client-side
   with libpq `PQencryptPasswordConn(..., "scram-sha-256")` (or an approved
   `psql` password workflow). Do not send a clear password in SQL text. Treat
   the verifier itself as sensitive: inspect statement/parameter/audit logging
   before sending it, suppress diagnostic SQL/driver exception output, and
   abort if it would be logged. Preserve role OID, privileges, memberships,
   LOGIN and all unrelated settings. No DDL/schema or data migration is needed.
6. **Coordinate database and files explicitly.** Commit the narrowly scoped
   database change, atomically replace each approved private consumer file,
   and activate the matching manifest last. Database commit and filesystem
   replacement are not one atomic transaction. Journal redacted stage states;
   incomplete activation must remain fail-closed with consumers stopped.
   Never silently restore the exposed password after a post-commit failure.
7. **Verify with fresh authenticated connections.** At the same exact role,
   database and approved TCP endpoint, first prove the new password works and
   identify the target; require the old password to fail with SQLSTATE28P01;
   then repeat the new-password positive control. A timeout, refused connection,
   absent role, peer/trust success, pool reuse or verifier inequality is not
   invalidation proof. Keep secrets and raw authentication errors out of output.
   This step is conditional on the qualified HBA rule, and cannot be performed
   on an isolated reference with no TCP listener without further authorization.
8. **Check consumers and isolation under their own authorization.** Confirm both
   staged consumers use the same new value, manifest hashes agree, privileges
   and schema are unchanged, and only then authorize reconnection/startup.
   A synthetic regression suite is not proof of production credential validity.

## Backups, clones and traces

Do not edit the cold bundle or historical backups. They retain the former
private credential and/or its database verifier. A rotation on one cluster does
not invalidate another copy. Maintain a redacted sidecar inventory outside
immutable bundles and require rotation before a restored copy gets application
or network access. Preserve isolated references until their separate remediation
is authorized. New working copies must not inherit a claim of sanitized secrets.

After authorized source remediation, create a separately authorized new matched
backup and verify recovery; retain the old one under the incident retention
decision. Archive encryption/off-host storage and disposal are separate actions.
Do not delete logs, rewrite history, change app retention settings or assume
local transcript removal also deletes remote/audit copies. Coordinate supported
trace handling with the account/workspace owner or service support using only
redacted evidence. If any credential reuse or trace scope remains uncertain,
retain `BLOCKED` rather than declaring `CONTAINED`.
